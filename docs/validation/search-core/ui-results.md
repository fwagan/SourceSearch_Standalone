# 可见 UI 验证结果（2026-10-08）

**结论：检索核心通过，UI 的100ms首屏目标尚未全面通过。** 不将本次原型标记为完整性能验收通过。

| 范围 | 核心36组正确性 | 核心最慢P95 | UI最慢P95 | UI超100ms组数 | UI报告有效 |
|---|---|---:|---:|---:|---|
| C# | 全部一致 | 38.75ms | 126.77ms | 4 / 36 | 是 |
| 混合文本 | 全部一致 | 14.15ms | 343.89ms | 7 / 36 | 是 |

所有组均为5次预热、30次样本、首批100行。UI使用正常可见的WPF窗口及与普通搜索共用的提交/发布路径，包含后台查询、Dispatcher恢复、结果绑定、布局和下一次`CompositionTarget.Rendering`检查点。并非显示器物理呈现时间。每组原始样本、候选数、首批行数、第一次执行及P50/P95/max均在JSON和逐查询表中。

| 独立记录 | C# | 混合文本 |
|---|---:|---:|
| UI进程打开快照 | 706.10ms | 421.81ms |
| UI进程首个查询到呈现检查点 | 190.45ms | 150.58ms |
| UI进程峰值工作集 | 501.43MiB | 798.33MiB |

混合文本 `a.b` 全字查询的核心暖P95为14.15ms，但该组首次执行750.76ms，说明大型候选行首次读取和归一化仍显著影响冷响应。每快照的256MiB候选行缓存是上述暖结果的条件。没有声称所有首次查询≤100ms。

最初C# UI有4组P95为117–126ms。经回归测试将逐条集合通知改为整批一次通知后，C#仍有4组超标，混合文本有7组超标。此优化没有消除长尾，因此没有重复跑到某次偶然通过。下一步应剖析UI绑定、布局、GC和渲染等待/系统调度，确定长尾来源，再选择UI层修正；本次没有证据把超时全部归因于某一个环节。
